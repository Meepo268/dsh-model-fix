## 解析与填充

- **配置解析优先级**：当前版本快照 → ≥ 最低支持的最高可解析快照（含更高版本，按当前 schema 降级解析，多余键忽略、`efforts` 宽松保留）→ 内置默认。更高版本快照降级落盘后**永不清理**，供再升级无损回退。当前版本快照非法**或残缺**时按**当前生效值**规范化重写——残缺会被 `parseSnapshot` 补默认判为合法，故须比对规范化结果而非只判非法。
- **`allowUpdate` 含缺失补写**，`autoFill` 关闭也拦不住：语义是"以目录为准同步该字段"。新旧相同则跳过，**数据无档位不删除已有配置**。
- **`force` 是单次绕过**（三项临时为真、不落存储、不重拉目录，避免把网络耗时算进按钮反馈）；与 compat 无关；`fix` 返回值只计模型变更数（compat 不计入，保持 RPC 反馈契约）。
- **`fix` 读 `descriptor.user`**（原始用户段）：避免规范化形态与写入形态不一致而反复触发重写。写回带 revision 围栏，冲突时重读重算（限次）；写失败先告警再抛出（事件侧吞 rejection，RPC 转 `ok:false`）。
- **空壳字段一律删除，判据只有一处 `stripEmptyFields`**（`reasoningEfforts` 为空对象或**只剩 off 键**、`input` 为空数组、`compat` 为空对象；宿主语义等同未声明——空对象自不必说，只剩 off 的档位表宿主校验也拒绝且 off 不具备推理语义，删除无损幂等）。**六条写回路径统一过它**——`fix` 填充、`reset` 重置、`restore` 恢复、`prune` 剔除（验证判定出档位不支持后的写回）、`fill` 探测式填充的预声明与收敛（两次写回共用 `planEffortApply`，只调一次）、探测兜底回退（`probe-backup` 把档位表按备份原值写回时），任何一处都不另写一份判据。只列这三个键：用户自定义字段一律保留，空壳是逐键核过的而非「通用空即删」——函数无空壳时返回**原引用**，调用方以引用相等判「这一条无需重建」。两处配套：`fix` 的缺失补写按**清理后**的值认（否则 `reasoningEfforts: {}` 既不被填又被清，得等下一轮才补上）；`reset` 的写回触发只看「带没带推理级别」（`Object.hasOwn`），否则带空壳的模型会被算进「重置 N 个模型」而虚高。`compat.ts` 的路由级整段 `unset` 是另一种作用域（不是模型字段清理），不经此函数。
- **compat「开启即添加、关闭即移除」，与模型参数取向相反**（后者关闭只是不写、存量保留）——`compat` 是本插件接管的路由字段，关掉开关却留着旧值等于开关没生效。当前两条规则共用同一协议 gate（`openai-completions`）与同一条写入路径：`disableDeveloper` 写 `compat.supportsDeveloperRole: false`（系统提示退回 `system`），`disableStore` 写 `compat.supportsStore: false`（请求体不带 `store` 键）；两者都**默认开启**——宿主对未在目录中标注的端点按「支持」处理（请求体带 `store: false`、系统提示用 `developer` 角色），本插件把取向翻成保守。**只写路由级不写模型级**（宿主里模型级优先，会与用户逐模型取值打架），且只对 `api === 'openai-completions'` 的路由写入。非目标协议（如已从 completions 切到 responses）无论开关如何仅做残留清理（只删不加）：原 chat-completion 时写入的 `supportsDeveloperRole` 与 `supportsStore` 字段不会因协议迁移而永久残留，但若 provider 无 `api` 字段则跳过（无法判定是迁移还是用户手动配置，宁不误删）。

## 排除与列表

- **`excludes` 是"零操作排除"**：命中者在 provider 循环入口整条跳过，填充 / compat / `force` 全不作用；已写入值原地保留——插件无字段来源记录，分不清插件写的与用户手写的，"清除"必然误删。瓦片释义与 README 须写明"仅对保存之后的行为生效"，正确顺序是**先加排除、再建提供方**。记忆剪枝已不归 `fix` 管（见「推理级别记忆」一节），`excludes` 只约束对 `llm-pi-ai` 配置的写入，而记忆存在自有段、由 `src/memory.ts` 按宿主全量模型列表剪，排除项与记忆再无交集。
- **必须允许填入不存在的 id**，故不做候选约束控件；UI 用「命中」表达"当前确有同名提供方、排除正在生效"，未命中是普通样式、**不得画成错误色**（0 命中也常驻）。命中判据取 `llm-pi-ai` user 层的 `providers` 键——与 `fix` 遍历同一份数据，零漂移。
- **不自动清理失效 id**（顺手 prune 会清空用户列表）：列表顺序是录入意图，脏检测用顺序敏感的逐位比较。去重分两层——录入端当场拒绝写入；`selfHealConfig` 兜住手改配置文件，仅当 `Set` 收窄后**变短**才产出 op。`fix` 的写回只写 `llm-pi-ai` 一段，**不碰自有 NS 的任何配置键**。

## 参数来源

- **图片模态只缓存正向信息**（纯文本省略以控体积；`pdf`/`video`/`audio` 忽略）。**容量哨兵**：`99999999` 与 0 一律视为无该字段（写 0 会被宿主 schema 拒绝并连累整批）。
- **id 匹配宁可漏不错配**：精确 → 词干 → 前缀三级，词干 / 前缀多命中即判无命中。词干拆为 `{base, digits}`，digits 取所有日期式数字组剥除连字符后的拼接，仅当两边都有 digits 才比对；任一边无 digits 则退回 base 兜底。三级匹配在**归一空间**进行：目录索引的 `ids` 存归一后的匹配键（目录 id 保留原始大小写与命名空间前缀，如 `tencent/Hy3`），条目本体由 `byId` 反查。定位分两级：**组内**依次试完整 id → 裸名 → **末段唯一匹配**，覆盖「本地带前缀 + 目录带前缀」「本地带前缀 + 目录不带」「本地裸名 + 目录带前缀」三种形态（前两级 key 相同时只查一次）；**全局**仅在跨提供方唯一命中时才认——同名条目常在多家网关重复，取第一个等于把别家的推理级别与容量写进用户配置。**末段唯一匹配只在 provider 严格匹配时启用**：用户指定了提供方即已定域，此时「裸名等于目录 id 末段且唯一」不构成歧义；兜底遍历与官方提示两处不启用——那里没有定域依据，裸名撞末段会把别家条目也纳入候选。同末段有多个**不同条目**时仍判歧义放弃。
- **缓存诚实保留目录的 off/none 拼写，不归一不合成**：models.dev 列了 `off` 或 `none` 才写入缓存的 efforts；`toggle` 不再据此合成关闭档（目录没给拼写就不替它猜）。`toReasoningEfforts` 将目录原值写入 `off` 键（`off:'none'` 或 `off:'off'`）而非 `null`——`null` 在宿主语义上是「省略参数」，对默认思考的网关等于没关。目录未列关闭档的模型，缓存的 efforts 里没有 off，`toReasoningEfforts` 产出不含 off 键的档位表，宿主按「该模型不能关闭思考」处理，UI 也不显示 Off 选项。
- **档位仅代表「能通」，不代表「能关」**：探测与验证都只判受理（收到 `block-start` 即判可用），不判端点是否真正遵从了 `reasoning_effort` 的语义。一个 `off` 能通（200 响应）不代表选它就能关闭思考——部分网关在默认思考时对任意 `reasoning_effort` 值都返回 200 却不改变行为。故探测不为未声明 off 的模型补 off 档（「能通」不构成「能关」的证据），已声明 off 的模型照常探测其原值、不做 `null`/`off`/`none` 拼写切换（一个 off 键只能携带一个拼写）。

## 推理级别记忆

- **`efforts` 是运行时记忆而非用户配置**：嵌套对象（model-id 可能含 `/`，拼接无法还原）、宽松解析（坏结构回落 `{}`，不判整段快照非法以免连累自愈重写）、`isDirty` 不比较它；卡片「保存」写整段快照时 `efforts` 取**写入当刻的实时值**（卡片不拥有该字段，用草稿副本会覆盖"开卡后切过模型"的那段记忆）。
- **Node 半只负责记忆的持久化与解析，不自动设置级别**（后端写配置只影响新会话）——自动恢复与自动设 `high` 必须走前端 `directory.select`，且自动设置不写记忆（经 `pendingAutoSet` 守卫跳过反向触发的投影变化）。**失效清理留在 Node 半**（见下条）——清理是纯数据操作，既不需要会话投影，前端也不必为此订阅宿主目录。
- **记忆清理归 Node 半、按宿主全量模型列表剪枝；`fix` 不参与记忆生命周期**：写入（effort-change）与恢复（model-select）留在浏览器半——两者都要会话投影，且设级别只能走前端 `directory.select`；清理两样都不需要：「模型还在不在」是 `ctx.llm` 的事实，Node 半直接查得到。清理若塞进 `fix` 则不自洽——`fix` 只认 llm-pi-ai 这一个事实源，写入面覆盖全模型而清理面只认 llm-pi-ai。独立触发（`llm/adapters-updated`、**两段配置变更后**、启动首轮）后覆盖面 = **宿主活路由上的全部模型**（llm-pi-ai、官方提供方、插件 adapter 注册的模型），而参数填充 / compat / `excludes` 仍只管 llm-pi-ai。**缺席即删除**（provider 不在 `listProviders()` 里 ⇒ 整段删；组内模型不在 ⇒ 删该模型，段删空则整个折叠），不采「宁残留不误删」：记忆不是要紧数据，丢了不过是不再自动设级别，而瓦片文案承诺的就是「删除模型或提供方时一并清除」，残留才是用户看得见的那个 bug。**唯「读不到」不等于「不存在」**：某 provider 在路由上但 `listModels` 抛错（未注册 adapter 即 `NO_ADAPTER`）时其整段原样保留；`listProviders()` 整体为空（退化读，什么都没加载出来）时本轮不剪。**档位是否仍被 `reasoning.efforts` 广告不参与剪枝**：档位表会漂移，而恢复侧 `advertisesEffort` 已守过一次，再加一道判据只会误删。成本可控：`listProviders()` 同步返回，`listModels` 只对**有记忆条目**的 provider 调（成本与记忆条目数成正比）；不用 `buildModelCatalog`——它逐模型 `resolveModelInfo`（可能打网络），且默认参数求值就会执行本插件未 inject 的 `ctx.agentDefaultModel`。写回仍经 `queueTask` + revision 围栏；在途时来的事件只置 pending、结束后补跑一轮。
- **`rememberEfforts` 关闭只停止"保存新的"**（effort-change 分支跳过），"恢复"照常取真实记忆；是否清空由卡片在开关由开转关时**立即**确认（经 settings scope 直写；"有记忆"判据取实时值，清空失败显式报错，避免开关已关而记忆未清无从察觉）。
- **`defaultHigh` 三条护栏**：记忆优先（有记忆即跳过，即便因不受支持而未恢复）、不覆盖既有级别、不干预同模型改级别（含手动选「provider default」）。它与 `rememberEfforts` 同属「用户体验」瓦片的同一条监听链，两个开关都**不读 `excludes`**。
- **浏览器半记忆写入的三条护栏**（`src/client/memory-listener.ts::rememberEffort`）：整段 `set`（非增量 path op）决定了基底必须是可信快照——ConfigForm 未 ready（status!=='ready' 或 revision 缺失）时快照 value 回落 `DEFAULT_CONFIG`，其 `efforts` 恒为 `{}`，以它为基底等于**清空全部记忆 + 写一条** → 直接放弃本次保存（记忆可丢，误清不可接受）。ready 状态下带 `expectedRevision` 围栏写入，`SETTINGS_CONFLICT` 时重读快照 + 重算 + 限次重试（与 Node 半 `updateMemory` / `writebackApi` 对称；判定跨半共享在 `src/shared/errors.ts::isSettingsConflict`），按旧段回放整段 set 会抹掉他方刚写入的记忆条目，故必须重读重算。非冲突错误（传输失败等）静默放过——记忆是可丢数据，失败不影响会话本身。

## 子智能体

- **子智能体推理级别在宿主 `agent/request` 瀑布里改写**：子智能体没有独立的推理级别设置面，浏览器侧对被寻址的子会话**根本没有 model-select 入口**（宿主 `sessions.subagentAddress` 主动屏蔽），而每次委派真正落地的那份调用配置流经 `agent/request` ⇒ 这是唯一既能读到「子智能体实际拿到的模型」又能写回档位的地方。种子配置被宿主 `deepFreeze`，故只能返回新对象；插件根 ctx 未打 scope 标签 ⇒ **单个 `{ prepend: true }` 监听覆盖全部 Agent**。
- **「跟随父智能体」开关以宿主那条设置为前提**：宿主「允许 Agent 为子智能体选择模型」**开着**时，子智能体的路由由父 Agent 每次委派自己在授权范围内挑，这时把子智能体钉回父当前的模型与档位会直接推翻模型的合法选择；**关着**（或该服务在 CLI/TUI 组合里缺席、或 `current()` 因「已开启但授权表为空」抛错）时，子智能体只有继承父路由这一条路，此时这个开关才决定它跟的是建子那一刻的快照、还是父会话的当前值。Node 半按三条皆满足才生效（见上文）。浏览器半现在也读这段宿主 settings 段（`src/client/composer.tsx` 的 `decodeHostModelSelection`，只读 `enabled` 布尔；宿主段缺席即视为未开启），用于输入框工具行的「跟随」状态灯（亮绿 = 实际生效中，灰 = 未生效）。卡片里的瓦片开关本身仍不置灰（用户翻瓦片就知道），但状态灯是 UI 层直接可见的生效态反馈。
- **「跟随父智能体」落在 `userExperience` 组内，不另起一个配置组**：它与同组三项一样是**会话侧体验开关**、与模型配置写入无关、同样**不读 `excludes`**（委派出去的子 Agent 与提供方排除无交集），另起一组只会让瓦片与版本快照平白多一处形态差异。它是一行布尔开关，复用该组既有的行内说明气泡即可，无需组总控。该键与 v8 新增的其他四个 userExperience 开关一起在同组落地，组内新增键向后兼容，因此不为它单独递增版本号（见 docs/versioning.md）。
- **跟随的是父 Agent「下一次请求该用的路由」**：先读父会话**待生效的选择**（`ctx.sessionProjections.stateOf(parent.session, 'modelSelection')?.pending`——UI 的每次切换落一条 `model/selection` 事件即置位，被匹配的那次请求消费掉才清空），读不到才回落最近一次请求头 `session.requestHeader()?.config`（无头再回落 `options`）。pending 优先是为了让子智能体与主智能体**同一条规则**：UI 里换模型或换档位后，主智能体的下一次请求直接用它，子智能体读同一份，不必等父先发一次请求把切换落到请求头上；常规委派路径上父每步都先写请求头再出网，两条路读到的值本就相同，差异只在被直接寻址发请求的派生会话上才显出来。`provider` / `model` / `reasoningEffort` 三项照父的来，`adapterDefaults?.reasoningEffort === true` 表示该档位是适配器默认值而非用户所选，跟随时删键（否则会把「没选」变成「选了适配器默认」）；待生效选择里没有档位即表示父此刻「选了模型未选档位」，同样删键。`maxTokens` 不照抄：父当前那份**不大于**子智能体当前那份（缺项视作不限）即取父的；父那份更大时只抬升差值的八成（`旧值 + (新值 − 旧值) × 0.8`，向下取整）——切到输出上限更大的模型后，旧的小预算会限制发挥，但直接顶到新值时部分端点会拒绝请求，「刚切模型就报 400」比发挥受限更糟。待生效选择里本就没有预算，故走 pending 时只看子智能体自己那份。**每请求现算、不缓存**——子智能体的模型与档位是建子那一刻的快照，但新委派的子智能体必然晚于父会话的每一次切换。
- **不预检档位可用性、不自动降级**：宿主在请求派发前按模型配置声明的档位本地校验（`resolveCallWithInfo`，见 host-api.md「llm：验证请求」），不支持的档位抛 `UNSUPPORTED_REASONING_EFFORT`，**未声明的档位根本不出网**。本仓跟随时写进去的是父 Agent **已经生效**的档位——同一条校验对父会话刚验过一遍，无从复检；而插件侧再查一遍还会与宿主判定漂移（配置与目录两处口径不一致时反而误伤）。故不做兜底、只让报错可见；本仓另有「验证模型」可由用户主动剔除不支持的档位，功能定位是**写配置**不是**替用户决定能用什么**。

## 写回端点

- **启动迁移的写回也带 `SETTINGS_CONFLICT` 限次重试，且重试必须重读重算**：启动期自有段不止迁移链在写——`dsh web` 一开客户端，浏览器半的记忆监听就可能直写 `efforts`，适配器拓扑事件触发的记忆剪枝同样写；恰插进迁移读-写之间时，冲突即本轮迁移写回丢失（新增配置项不落盘，直到下一次成功的启动，且只剩一条难以察觉的 warn）。重算而非回放：冲突说明他方已改段，按旧段算出的整段 `set` 若只换个新 revision 回放，会把他方刚写入的内容整个盖掉；重读后重算，他方已补齐的字段让 op 自然收敛为零。
- **`queueTask` 在 hmr 注入落地前有界等待，而非组件级依赖、也非缓冲队列**：hmr 模块异步装载，注入落地前的写回会退化为裸 `task()` 裸跑进宿主事务上下文（写入判定抖动窗口）。等待在写回收口处做：注入落地（值缺席也算落地，降级判定在等待之后）即放行、模块加载起单一计时器封顶、只等一次。**不把 `hmr` 加进组件级 `inject`**——cordis 的 PENDING 无超时，hmr 缺席的环境会让整插件永久挂起且零日志，用整插件激活权去赌一个私有字段（`executing`，非公共 API 面）风险倒挂；**也不用「als 未定义先缓冲、`set` 时回放」的队列**——hmr 永不到达时缓冲任务永挂，比超时降级危险得多。超时降级后的行为与历史版本一致。
- **重置推理级别不写配置段、不改开关**（关掉开关等于修改配置，用户不一定要）：只剔除 `reasoningEfforts`，容量 / 输出上限 / 图片模态与自定义字段保留。竞态防护靠 Node 半模块级计数守卫（置位先于 mutate 同步完成，覆盖写回同步派发的事件；持有可嵌套、解除只折抵一次置位，先结束者不解掉仍在途者的守卫），`forceUpdate` 端点同样被守卫拒绝。
- **恢复备份对共有 provider 既回退又复活**：备份与当前都存在的 provider，其共有 model 回退到备份值，该 provider 下被删的 model 一并复活（当前 `models` 键缺失按「删光」处理，同样全量复活），按备份原序追加到末尾，计入「已恢复 N 个模型」。**被整删的 provider 不复活**——它连同 api-key 一起没了，复活等于看得见用不了；启动后新增的 provider/model 原样保留。备份是 model **整对象**快照，故用户手写的同名键一起回退。备份只在 `apply` 最顶部捕获一次、仅存内存，**绝不做延迟补捕**——晚于写回捕到的是被填充过的内容，比没有更危险。备份缺失或当前无 `providers` 段要**显式抛错**（回 0 会显示成「已恢复 0 个模型」，与"确实无可恢复"无法区分）。
- **剔除不被支持的档位走 Node 半（守卫不可省）**：这条写回若落在浏览器半，会被本插件的事件链当成「配置变了」触发 `fix`，把刚剔掉的档位从 models.dev 又填回来，用户点了剔除却什么都没变。守卫（`src/guard.ts`）是 Node 半的模块级计数（可嵌套持有、解除按次折抵），浏览器半跨不过半纯度门禁，故经 `queueTask` 写回、与其他写回端点以守卫互斥、revision 冲突重试。确认框照「清空推理级别记忆」那层二次确认，两键文案换成「剔除」。
  - **不支持档位明细由 Node 半直接给出**（`VerifySummary.unsupportedEfforts`）：统计值前端直接用，不必自己从 `results` 里重算；而剔除要写配置就得逐条定位，那块不聚合只给明细——两处各筛一遍，口径一旦分叉就会漏剔或多剔。
  - **只认「明确判为不支持」**：超时、限流、额度耗尽、端点不可达都只是**没验成**，不是不支持，拿它们去删用户填的配置就是误伤。`pruned` 只计真正从现有档位表里剔掉的条数——确认框里的 `n` 与结果里的 `x` 可能不等，那是如实而非出错。**剔除结果一律照实显示条数、为 0 也不例外**（单一 `pruneDone` 文案，不另设「无须剔除」分支）：目标在剔除期间已被用户改掉、或其提供方正落在排除列表里时（`planPruneEfforts` 整组跳过，且不撤销已写入的内容），0 就是真实结果。**剔除结束后关闭弹层**：结果写在卡片状态行上，不关窗用户根本看不到。
  - **幂等**：目标里那些当前已不在档位表中的（验明确认之后用户自己改过）一律不命中，零写入也不虚报。
  - **尊重 `excludes`**：排除语义对本插件的写入处处生效，不因这次由用户发起而破例（验证只读，写入才受限；探测式填充那两次写回的唯一例外见其小节）。
  - **档位被剔空时在写入前就判定**：让整个 `reasoningEfforts` 键不出现在新值里——本仓写回只整段覆盖（不写数组下标中间段），空壳留着会反复触发写入判定。
  - **自动填充不会把结果翻回去**：用户手填的档位被填回是正常的（models.dev 说它该在那儿）；模型页上已有推理级别的模型本就跳过填充；真被剔到零的只可能是全手填的模型，剔空后该字段整个消失，模型回到「未声明档位」态，此后也不会被填充。

## 验证

- **验证是只读诊断、只由用户主动发起**：不随填充后台自动验证（`fix` 是事件热路径且每次重试重读 revision，掺入网络 I/O 会让 `SETTINGS_CONFLICT` 反复重算重验；「已验证」账本还须新增顶层配置组并升级，且凭据/模型一变即过期）。结果**即用即弃**：不写 settings、不占事件流守卫、不与三个写回端点互斥、也不进配置键；列表**不套用 `excludes`**（排除只约束对配置的写入）。
- **验证只判「适配器是否开始产出内容块」，不判内容**：提示词仅 `Just say OK`，收到首个 `block-start` 块即判成功并立即中断（省额度）；只看返回文本会把不按提示词作答但实际可用的模型误判为不可用。**不可写成「首个非 `finish` 块」**——`usage` 块不含受理信息，额度耗尽的 key 实测也会先来一条，那会把用不了的 key 判成可用（宿主 `isVisibleChunk` 同样把 `usage` / `finish` 排除在「内容」之外）。全程无内容块、`error` / `aborted` 终止、异常与超时一律判不可用。档位 id 取 `reasoningEfforts` 的键（即模型页送出的同一个值），候选列表与档位探测顺序按 `EFFORT_LEVELS`（`off < minimal < low < medium < high < xhigh < max`）排序。
- **失败分类只认 `code`，全程不比对文案；短路只有一条判据、分两级**：宿主 `HarnessError.code` 明令「route on this, never by parsing `message`」，故一律不比对报错文案。**`status` 一律不看**：pi-ai 侧抛错只给 `new LlmError(message, code)`、终止错误也只给 `{ message, code }`，任何上游状态码（400、5xx）在到达我们之前就被压成文案（`classifyPiAiError` 正是跑正则从文案里认 code）。据此分类：档位不被支持（`UNSUPPORTED_REASONING_EFFORT`，宿主在派发前本地拒绝，请求根本没发出去）/ 额度耗尽（`QUOTA`、`ACCOUNT_QUOTA`——后者是宿主 error.js 给「账户余额不足」定的字面量；额度可能只覆盖其中某个模型，故只压该模型、不压整组）/ 凭据无效（`INVALID_CREDENTIAL`、`MISSING_CREDENTIAL`）/ 端点不可达（**只认传输层失败码 `TRANSPORT` / `STREAM_CLOSED`**）/ 限流与超时（`RATE_LIMIT`、`TIMEOUT`，**单列为瞬态**：它们只否定这一次，既不算不可用、也不短该模型的后续档位——实测 429 挡掉的档位隔一会儿就通，判死会把好档位误送进剔除清单；判定依据是宿主 retry-policy 的 `DEFAULT_RETRYABLE_CODES` 里除传输层与 `EMPTY_RESPONSE` 外的那几个；**唯一例外是探测式填充**：它把限流短到该模型的档位尾——被短模型本就「没跑满即还原」档位表，短路只省请求、没有误杀好档位的风险（见「探测式填充」））/ 其它。**「`status` 缺失即不可达」是错的**——实测踩过：上游一次 400 因文案里没字面出现 `400`/`invalid_request`，宿主给的是未识别码，于是掉进那条兜底被误判成断线，provider 剩下的模型全被跳过。`EMPTY_RESPONSE`（成功抵达却零内容块）同样归「其它」，它本就不是失败。在此之上另有一级**模型级**短路，判据与 provider 级同源，只剩一条：**能断定后续请求必然失败才短**。档位请求上只有额度耗尽够格（同一把 key 对这个模型的额度已见底，换多少档都是同样结果），只有换模型才可能不同，故只压该模型自己的档位、不牵连同组其余模型。其余一律不短，宁可多烧几次额度也不误杀：上游 5xx 与其它厂商侧拒绝多半是服务端的一次性故障，换个档位可能就通；限流与超时只否定了这一次；「档位不支持」恰是唯一值得继续逐档位验的结论。只对带失败事实的探测生效：正常终止却没有内容块属退化完成而非报错，换档位仍可能出内容。
  - **「探测」是不带 `reasoningEffort` 的对照请求，由浏览器半声明要不要发，它不是被验对象**：本插件的「不支持」信号来自上游 4xx，而 4xx 在上游那里是 invalid_request 的统称，按 `code` 分不出「档位不支持」与「参数写错」。探测提供对照——不带档位都跑不通的模型，换任何档位也是同样结果，没必要把每个档位各烧一次；跑得通的模型再逐档位验，失败才可能归因到档位。**是否需要探测由计划里每个模型的 `needTest` 声明，Node 半不替浏览器半反推**：关掉档位开关时全部请求本就不带参数、模型压根没声明档位时也没有档位可比——这两种情形下那一次不带档位的请求**本身就是被验对象**，再补一条纯属白烧额度（无档位却声明要探测按非法入参拒绝）。探测**不进计划、不进明细、不计任何统计**，跑通时也不发进度帧：故记录里每一条都是被验的那一次，帧上的「还剩几条没验」也与实际待验条数对得上。**唯一的例外是探测失败**：限流与超时只否定了这一次、不据此短路，但同样要留一条模型级记录交代它为什么没过；其余失败则据此短路——那个模型一条都没验成，不发记录它就在记录区彻底消失，用户只看到别的模型的结果，无从知道它为什么没出现；故此时发一条**不带档位的模型级记录**（撞上端点不通 / 凭据无效则发提供方级），`skipped` 含探测自身——它同样没发出去。它只参与两件事——当档位结论的对照，以及在撞上端点不通 / 凭据无效时如实反映到该组的 `reachable` / `keyValid`（它也是真发出去的一次请求，不许当它没发生过）。为免「计划里没有它、计数却涨了它」，上限按**真正发出的请求数**（档位数 + 探测数）计。
  - **判「档位不支持」的两个条件**：探测已通过 + 该档位被判为**参数不正确**（`INVALID_REQUEST`）。第二个条件取的是宿主 `classifyPiAiError` 已经从文案里归一好的结论——**我们不再自己比对任何文案**。控制变量法已经足够：基线（不带档位）通过了，说明端点、凭据、额度、网络、模型名全部无碍，两次请求唯一的变量就是档位。
  **同一提供方共用同一 url 与同一把 key**，故「端点不可达 / 凭据无效」一旦出现，该组剩余请求必然同样失败，立即短路——省下的额度就是省下的钱。**唯一追加的 provider 级是「本组首个请求就超时」**：成因在请求之外（url 不可达、端点服务中断、本地网络不通），后面几十条请求只会是同样无意义的超时；理由记 `timeout` 而**不是** `unreachable`——超时不是传输层失败的证据，把「可达」翻假会让用户以为端点已确认连不上。首个之后的超时不同，那时链路已经跑通过，只是这一次慢。额度耗尽只压当前模型（它多半是**按模型**设的，有的厂商给某个模型单独限额），**既不压整组也不否凭据**：`keyValid` 说的是整把 key 有没有效，拿一个模型的额度去否定它是层级错配，要看出什么事得看该模型自己的明细条目。档位不被支持属逐模型逐档位的个体结论，只记录不短路；其它厂商侧拒绝（如该模型不存在）同理。**我方超时不算端点不可达**（首个那条除外）：慢端点不该被当成断线，它与限流同归瞬态，如实记进明细，但不据此判不可用、也不短该模型的后续档位；抛出的异常归入「其它」——宁可不短路，不可误短路。
- **验证结果同时给明细与统计**：统计（逐提供方的可达 / 凭据 / 可用数 / 是否短路，加全局计数）供一眼看完；**明细 `results` 逐条给出「提供方 / 模型 / 档位 / 结论 / 失败原始事实」**，供后续拿明细做操作（只重验某个提供方、只补验某些档位、按 `code` 细分失败原因等）。明细只含**实际发出**的被验请求——探测不是被验对象，不在其中（它对档位结论的作用在明细之外体现）；被短路掉的从未发出去、没有结论可言；哪几条没跑由逐提供方的 `planned` 与 `probed` 之差给出（短路以整组为单位，按组定位即可）。`tested` 取自计划而非明细，故「用户勾了几个」不会因某模型被整体短路而少算。**收尾那行文案随档位开关分两档，数字口径跟着「档位」的含义走**：关档位时请求本就不带参数、没有级别可报，故报「勾选 `tested` 个 / 可用 `models` 个」；开档位时级别分母取 **`plannedEfforts`**（计划里带档位的条目数）——`planned` 还含「没声明档位的模型」那一条（它验的是模型），拿它当分母会让「X / Y 个推理级别」凭空多出一个，用户会以为有档位没验成。而档位开关开着却一个级别都没计划时（勾选的模型都没声明档位）退回模型口径：那行只会显示「0 / 0」，比不给结论还糟。`failure` 保留宿主原始 `code` / `status` / `message`：`code` 供调用方做比本插件更细的分类，`message` **仅供展示与诊断**，分类绝不可依赖它。
- **每 provider 单并发、跨 provider 最多 5 路、不做退避重试**：一个 provider 一条串行链（`groupProbesByProvider` 的分组即结构保证），前一次返回才发下一次以规避 429。请求总数封顶 200（逐模型逐档位展开会累积条目，探测也算一次请求，超出即拒绝而非静默截断）。列表**默认不预选**、关窗即丢弃勾选：验证花真实额度，预选全部等于把「误点即扣费」变成默认路径。分组头另给「全选 / 取消全选」小键——验证某一提供方的全部模型是高频操作，逐条勾选太慢；键的组件、尺寸、文案逐条照官方 `candidateToolbar` 的 ghost 小键，文案判据用 **`every`**（部分选中时仍显「全选」，全选中才翻成「取消全选」，与官方 `allVisibleCandidatesPicked` 同语义）。该键仍需用户主动点击，不因此改为预选。**文案判据与点击方向必须共用 `groupAllPicked` 这一个纯函数**：两处各写一遍 `every` 一旦不同步，就会出现「文案显示取消全选、点击却是全选」的反直觉行为且不报错。该函数与 `toggleGroupPicks` 一并落在 `client/model.ts`（不留在组件内），与瓦片总控的 `masterValue`/`applyGroup` 同构，因而能被 `test/` 覆盖——选择代数留在组件闭包里就等于没有测试。
- **验证弹层自确认**：候选框内已有 warn 额度提示与 warn 语义验证键（`.dsh-mf-warn`），构成自确认故不再叠二次确认弹层；**卡片 footer 的「验证模型」触发键同样取 warn 语义**——点开即进入要花额度的流程，警示前移到入口比藏进弹层更有效。它是 `.dsh-mf-discard` 叠加 `.dsh-mf-warn`（类名特异性与聚焦环见 `card-styles.ts` 注释）。类名不叫 `confirmWarn` 而叫 `warn`：触发键与确认键共用同一套 warn 样式，`confirm` 前缀会误导读者以为只用于确认。footer 内因此有两个 warn 键，靠位置与文案区分。
- **档位开关关掉时不发 `reasoningEffort` 参数**：端点可能有自己的默认推理级别，不带参数验的才是用户实际会走的那条路径。开关文案「验证推理级别」同时覆盖两态。两种模式下未声明档位的模型都只发一次不带参数的请求——开态对它没有可验的档位，与关态同形。**档位开关与两键并排同一行、开关靠左**；**记录区在弹层内单列为选项卡**（见下条），footer 只剩取消/确认两键，自绘纵向容器一并删掉，底部交给宿主 `.footer` 自身的 `flex-end + gap:8px`。纵向间距不再逐处取档位，改为**弹层正文内部一律 12px**：各段套一层 `.dsh-mf-verifyBody`（`flex column + gap:12px`）把节奏收在一处、各段自身 margin 归零；**列表项间距用默认（不写 gap，即 0）**。数值与取舍理由见 `card-styles.ts` 的注释。在途期间弹层原地转圈（宿主 `StateDot` 的 `ongoing` 态即转圈本体，置于确认键内部作首个子节点——宿主 Button 自身是 `inline-flex` + `gap`，零额外 CSS），跑完不关窗，结论追加成记录区末行、**不再往卡片状态行渗透**，由用户看完自行关窗——结论此刻就在用户眼前，再抄一份到关窗后才可见的地方只是把信息挪到视线之外；除验证外的操作结果才一律走卡片内联状态行——逐条冒出来的记录只交代过程、不交代「总共怎么样」，否则用户只能自己数末行才知道结论。在途的确认键文案为「停止」：弹层有出口，键不变会让用户只能干等（取消键仍按原样在途中禁用，取缔的是「无路可走」而非「关窗 = 停止」这层意思）。
- **验证弹层的记录区单列为一个选项卡，与模型列表并列**：记录是「正在发生的事」，模型列表是「挑哪些模型去验」，同处一屏只会互相挤——跑起来时正文被记录区顶开、勾选区被推出视野。故正文顶层改为两个选项卡（模型列表 / 验证记录），额度提示提到选项卡条之上、两个面板之外（它讲的是「这轮会做什么」，对两页都成立，不该只归其中一页）。**发跑后等记录区渲染再切记录页**：发跑由 `useEffect` 监听 `running && total > 0` 触发切换——`total>0` 是 `TerminalBlock` 的挂载条件，切过去那一刻记录区已就位，不会先闪空态「未发起验证」再异步刷出内容；用 effect 而非按钮同步跳转，是因为 `opened` 帧来自异步 SSE 流、同步跳转拿不到数据。**每次开窗回「模型列表」**：关窗已丢弃上一轮的勾选与记录，落在空记录页只会让人以为记录还在。**两个面板都常驻挂载、切页只改 `hidden`**（与官方那份 `visitedIds` 同一用意）：记录区的 `TerminalBlock` 自带展开 / 收起状态，卸载即丢；还没发起过（`total === 0`）时记录页给一行空态而非空白面板。条与面板的 `role` / `aria-selected` / `aria-controls` / `data-active` / 未选中 `tabIndex:-1` / 方向键循环与 Home / End 后移焦，以及选项卡条的样式数值，逐条复刻官方「设置 → 内置插件」的插件视图选项卡（`PluginsSettingsSection`）——宿主没导出同款原语，故本地自绘；唯面板上方的留白不取官方的 `padding-top:2px`——本项目的正文一律 12px 更优先，那 12px 由 `.dsh-mf-verifyBody` 的 gap 给；不取 `SegmentedTabs`，那是分段控件、形态不同。
- **两个弹层的退出键一律叫「取消」，且在途不禁用**：宿主 Modal 在任何时刻都能被遮罩 / Escape / × 关掉，四个出口本就等价；出口键若禁掉，用户想中止只能去点遮罩（那还顺手把记录丢了）。禁用只留给在途真正会互相打架的控件（档位开关、勾选与组开关）。键面文案统一取「取消」：卡片 footer 的退出键、二次确认层的退出键都是「取消」，同一件事（不执行当前操作）换词只会让人以为是几种动作；`close` 键因此只留在宿主 Modal 的 `closeLabel`（× 的 aria-label），那处要的正是「关闭」这个图标键的语义名。
- **进度走 SSE 流**：验证可能跑数分钟，UI 只能转圈等于让用户猜是不是卡死。宿主装插件时的实时输出来自 **pnpm 子进程 stdout → Cordis 事件 `plugin-manager/install-log` → WebSocket 多路复用**，但事件转发走的是 `DSH/packages/api/remotes/src/remote-events.ts` 里一份**编译期常量白名单**（27 条），第三方事件永远不会被派发；`@Remote({ mode: 'stream' })` 虽 Host 侧可发现，客户端却要求 Typert 编译器产出的 strict codec，且挂载清单同样是硬编码——**第三方挂 stream Remote 没有先例**，为一次诊断进度引入整套代码生成，风险收益不成立。改走 `connection.fetch.register` 的 exact 路由：`new Response(ReadableStream)` 是官方 `session-log-export` 正在跑的同型用法，且白拿信任围栏、浏览器认证与「客户端断开 → `request.signal`」（`DSH/packages/client/connection/src/http-bridge.ts` 把 abort 挂在 `res` 的 `close` 而非 `req`——Node 16+ 的 `req.close` 会在请求体读完就触发，把刚开的流掐掉）。内容类型取 `text/event-stream` 虽不写 SSE 客户端，却能绕开 gzip 中间件——它**显式跳过**该类型（`DSH/packages/host/webserver/src/index.ts`），普通类型一旦被压缩缓冲，流式就没了。浏览器侧用 `fetch` + `getReader()` 而非 `EventSource`：后者自动重连，而重连等于重跑整轮验证。
- **关窗 / 断连 / 点停止一律中止**：流式之后连接的生命周期**就是**这次验证的生命周期，断开即中止，Node 半据此让执行循环早停（只断在途请求而继续循环，后续探测会带着已中止的信号跑出一串假失败）。因此弹层的遮罩 / Escape / × 与「停止」键全都汇入同一个 `AbortController`。**中止不发终帧**：消费方见「流自然结束却没等到终帧」即知这轮没跑完，据此保留进度。被中止时弹层不关、已打出的行留着，主键复原可重跑（重跑会清空记录，免得上一轮的残留行混进这一轮）；记录区的 settle 文案取「已停止」——用户主动停止不是失败，不该落 `error` 态。**「停止」按下即在记录区追加一行「已停止，本轮不再继续…」**：它是唯一不关窗的中止方式——遮罩 / Escape / × / 「取消」键那几种的记录都随弹窗一起丢掉了，只有它留下的进度用户还看得见；中止这件事该落在日志里，而不只是那个「改了就改了」的 `done` 状态标签（标签只有两个字，说不清是本轮到此为止还是仍会继续）。两个弹层同一处理，措辞刻意只说「不再继续」、不说「已还原」——后者是探测式填充中止后的事实（那轮整轮还原），而验证是只读诊断、压根不改任何东西，写上去反而不准。
- **wire 只发结构化帧，文案与格式化全在浏览器半**：locale 只存在于浏览器半（`src/client/locale-zh.ts` 与 `locale-en.ts`），文案归 Node 半就等于把本地化绑死在 Node 产物上，改语言要重发 Node 半。故进度帧是判别联合（`opened` / `probed` / `done` / `failed`），显示词与行模板（`{provider}: {model} [{effort}]：{result}`，层级用冒号而非斜杠——模型 id 自身就含斜杠，如 `z-ai/glm-5`，拿它当分隔符读不出层级）由浏览器半拼。`probed.skipped` 在该结论短路了后续请求时出现（provider 级或模型级，含探测不通导致的短路），值是未发出的条数——消费方才好交代「这组还剩几条没验」。**进度 `done`/`total` 与各统计口径一致：`total` 只数计划条目（基线探测不是被验对象，不占分母），`done` 数已了结的条目——被短路而未发出的同样计入，故 `done ≤ total` 恒成立、整轮跑完即 `done === total`；交代基线为什么没过的模型级记录是「附注帧」，不推进 `done`**。`decodeProgressFrame` 逐字段校验而非 `JSON.parse` 了事：`done.summary` 直接驱动卡片上的统计数字，形状不对却当成合法帧用，等于把 `undefined` 当 0 展示。provider 级失败行不带模型与档位（那不是某个模型的问题，是整组都不成立），非 provider 级才补档位词。**失败与中止分两条路**：执行器抛错（入参非法 / 超配额 / 中途异常）收于 `failed` 终帧，`message` 是 Node 半的中文原因，消费方原样展示——裸报「已停止」会把「勾选超出上限」这类原因整个吞掉；中止则**不发任何终帧**，消费方据「流结束却无终帧」判中止，故「有没有终帧」就是失败与中止的判据。**Node 半不为 `failed` 另打服务端日志**：原因已随终帧抵达浏览器半并被展示，服务端再打一份是重复，且会在测试输出里刷出与实际失败无关的堆栈。

## 探测式填充

- **探测式填充（逐档试出可用的推理级别并立即补全）**：与验证同一条 `connection.fetch` 流、同一个执行引擎（共用的一半按职责分四层：`src/probe-verdict.ts` 收失败分类与两级短路判据，`src/probe-plan.ts` 收入参校验与计划展开、按提供方分组与两条硬闸配额，`src/probe-engine.ts` 收单次请求与受理判据与并发编排与进度帧，`src/probe-report.ts` 收逐组汇报与全局汇总；两者只差「一组里怎么逐条跑」这个 `runGroup`），差异只有下面几条。
  - **必须先把候选档位临时预声明进配置，探测才有意义**：宿主在派发前按**模型配置里声明的档位**本地校验（`resolveCallWithInfo`，见 `host-api.md`「llm：验证请求」），未声明的档位不出网、只本地抛 `UNSUPPORTED_REASONING_EFFORT`。所以「探测一个没声明档位的模型支持哪几档」在配置不动的前提下根本无从谈起——至多七档（off 仅已声明时才探测）全被本地拒。预声明是本功能的必要前置而非副作用：它在同一轮结束时被收敛写回收回，且增删统计以**预声明之前**的档位表为基线，临时档位既不计新增也不计删除。
  - **收敛写回在流内完成，终帧最后发**：`VerifySummary.fill`（模型数 / 新增 / 删除）是探测式填充专有字段，验证恒缺省。之所以不另开一个 `fillEfforts` 写回端点，是因为收敛要用到「预声明之前的那份档位表」，那份状态只在 Node 半这一轮里；拆成两个调用就得让浏览器半把它自己看到的旧表回传，而浏览器半的快照可能已经过期（用户在探测期间改过配置），据此写回会把用户刚改的档位翻回去。
  - **两级短路的判据与验证同源，只剩一条「能断定后续必然失败才短」**：provider 级是 `providerBlockReason(outcome, firstRequest)`（端点不通 / 凭据无效 / 本组首个请求超时），模型级是共用判据 `shouldSkipModelTail(outcome, failure)`（档位请求上只有**额度耗尽**够格）外加**本功能自有的限流**——两者都**只短到该模型自己的档位尾**：同一把 key 对这个模型的额度已见底，换多少档、换哪个模型都是同样结果，继续逐档试纯属烧额度和时间，用户要的「这一档行不行」在第一次就已经没有答案了。限流在验证里不短（429 挡掉的档位隔一会儿就通，判死会把好档位误送进剔除清单），在本功能则短：限流不分档位，同一窗口内同一把 key 对该模型剩余档位的请求大概率同样 429，续发只会再添 429；而被短的模型本就走「没跑满即还原」（档位表原样不动、没有误杀档位），短路只省请求。上游 5xx、其它厂商侧拒绝、超时一律不短（多半是一次性故障，或只否定了这一次），宁可多烧几次额度也不误杀可用档位。本功能没有基线探测，故「其它厂商侧拒绝」落在档位请求上时**不再**构成模型级短路——那是验证侧 `shouldSkipModelTailAfterBaseline` 才认的，那里的请求压根不带档位。被短路的模型按下面「没跑满即还原」处理，本功能不必新增任何收敛逻辑。
  - **不搬验证的「每模型额外一次基线探测」**：本功能的对照比基线更紧——更低档跑通 ⇒ 端点、凭据、额度、网络、模型名都无碍，唯一的变量就是这一档，而代价为零；基线唯一多换来的是「`off` 自己也能被判不支持」，但 off 被拒不判不支持并不影响补全（其余档照补、照记），却要让每个模型多烧一次请求（本功能正是额度开销最大的那个）。
  - **判「这一档不支持」的第二条件换成「同模型已有更低档跑通」**：验证有专门的基线请求，本功能的基线就是预声明 + 已跑通的更低档（更低的档已通 ⇒ 端点、凭据、额度、网络、模型名都无碍，唯一剩下的变量就是这一档）。第一档就被判 `INVALID_REQUEST` 时第二条件不成立，只记「其它」——那更可能是模型本身的问题，判成档位不支持会把一个其实能用的档位误判掉。
  - **自动写入开启时，两种收敛口径都由「剔除不支持」开关选**：关 = `可用 ∪ 原有`（只增不减），开 = `可用 ∪ (原有 − 明确判不支持)`。两条都只认明确状态：限流、超时、额度耗尽、端点不可达都只是「没验成」，既不算可用也不算不支持，拿它们去动用户配置就是误伤。档位表算空即整个 `reasoningEfforts` 键删掉（回到未声明态），与剔除路径同一形态。
  - **「剔除不支持」只对「探测所有」有效**：走「探测未填充」的模型本来就没声明过档位，判不支持的那几档压根不会写进去，无从剔起；那一轮里浏览器半直接按「关」下发并在途禁掉开关，避免留一个亮着却不生效的开关骗人。
  - **没跑满结论的一律还原，中止则整轮还原**：某模型的请求没拿满（被 provider 级或模型级短路连带）就**不动它的档位表**，直接还原成预声明之前的样子。本轮被中止时更进一步——**整轮**还原，连已跑满（至多七档）的模型也不补、不剔：用户按「停止」要的是原样停下，不是「探到一半、填一半」。半截结论不足以动用户配置，而「探到多少补多少」的结果既不可预期、也可能把半截结论写成定论。
  - **探测式填充的写回范围以点开弹层时冻结的候选清单为准，两次写回都不读 `excludes`**：「忽略排除」只作用于**探测范围**（那份候选清单含不含被排除的提供方）。原先写回也读 `excludes`、靠「两边必须共用同一个值」保证范围一致，但两次读的是不同时刻的配置——轮次中途新增的排除会让收敛整组跳过，预声明再也收不回来且此后无路径回收（兜底备份在收敛落盘后就清了，`fix` 不碰档位、`prune` 只删验证判定不支持的，下一轮因仍在排除里照跳不误）。范围只由清单决定即天然一致：预声明写了谁，收敛就还谁，轮次中途的排除留到下一轮生效（与守卫「一轮探测期间其它写入被拒」同一口径）。附带后果：写回不再读自有段，故自有段读不到不再牵连「不算失败」；但兜底备份要写进自有段，仍是**整轮中止**——没有退路就不动用户配置。
  - **开跑前把探测目标的档位表原值备一份，启动末尾见键即撤回**：崩在中途时进程已经没了，收敛没有机会跑，预声明就留在用户配置里，而插件也不知道该收敛成什么样，落盘的那份是唯一退路。**只备探测目标的那一个字段**（`reasoningEfforts` 的原值深拷贝，含用户自己的 wire 拼写；原本没有该字段记 `null` 哨兵，回退时删键），不备整段 providers——预声明的范围在开跑时即已冻结（见上「写回范围以候选清单为准」），整段备份唯一的额外作用是覆盖范围外的模型，而那只会连带撤销用户在探测期间对范围外模型、以及同批目标模型其余字段的正当编辑。回退据此只撤档位表：**不复活**用户在窗口内删掉的模型（提供方被整删、模型被删都跳过），也不碰同一模型的其他字段。编码**只做 base64 不做压缩**：内容只有几批目标模型的档位表，压不动多少，而 base64 是为了让自有段里存的是一行无引号无换行的纯文本（否则那段 JSON 得整段转义塞进配置）；顶层键不进版本快照，故**不动 `CONFIG_VERSION`**。存不下即整轮中止。位置在启动链末尾、首轮 `fix` 之后（迁移与填充在前），回退后再补一轮 `fix`，否则被撤掉预声明的模型会停在未填充态、主功能失效。解不出内容即丢弃且不回退（旧形状的整段备份解不出，升级跨越的那一轮探测预声明无法自动回收，属可接受的降级）；**回退成功才清备份**，防止回退本身失败时退路先没了。
  - **清备份放在收敛落盘之后的最后一步**：唯一残留窗口是「收敛已落盘、备份还没清」时被杀，下次启动会把这一轮**已成功**的补全一并回退（多探一遍即可重来）；反过来先清后备着，崩在收敛之前就无人回收预声明，把用户配置留在半截状态，更糟。清不掉只告警，不把已成功的补全报成失败。
  - **中止恢复走内存基线，不复用那份落盘备份**：中止时进程还在，`declareProbeEfforts` 返回的 `preexisting`（预声明之前每个模型的档位表，无档位记空表）足以把本轮动过的 `reasoningEfforts` 原样写回，粒度更细、零落盘零解压；若改走备份，就得连没碰过的模型和字段一并按备份覆盖，误伤面反而更大。两类故障的交汇处是有覆盖的：中止后收敛写回本身失败抛错时清备份不会执行，备份留在段里，下次启动幂等回退。
  - **事件流守卫持有整轮**（预声明 → 探测 → 收敛之间不放开）：放开的话，用户或别的插件在这几分钟里改一次配置就会触发 `fix`，把预声明按 models.dev 改回去，探测剩余的请求会被宿主本地拒绝、结论全错。代价是一轮探测期间其它写回端点被拒、自动填充暂停——一轮探测本就是用户主动发起的，且带着未收敛的写回，放开守卫的风险比让出这段时间更大。探测流入口也因此先查守卫，与写回端点互斥（守卫为计数，故并发探测不会双双通过）。
  - **收尾不自动关窗**：跑完立刻关窗会把读结论变成限时任务——「自动写入」可关后收尾有两种形态（写回并汇报 / 只汇报不写入），且跑完与失败反正都留在窗内、结论就在记录区末行，由用户看完自行关窗即可。
  - **配额按模型数封顶 200（至多 1400 次最小请求），超出整体拒绝**：沿用验证「不静默截断」的纪律——截断会让用户以为「全查过了」。与验证的 200 次请求上限是同一个量级的东西，故两条硬闸写进同一个 `planProbes` 的 `ProbeLimits`。
  - **「自动写入」关闭即整轮不落结论**：探测照常预声明与执行（不预声明就出不了网，与开关无关），收敛结论照算但不落盘——所有模型原样还原预声明之前的档位表（与中止同一形态、同一写回路径，内存基线非落盘备份）；终帧的 `fill` 照带，含义变为「可补全」的假设统计（结论若写入的增删——关掉开关的用户也该看到这轮探出了什么），浏览器半换措辞报一行「可补全…未执行写入」、不落卡片状态行（没写回就没有「已补全」可言）。开关默认开且**每次开窗重置为开**；Node 半对缺省键取**开**——其余两开关缺省为关是「不做额外的事」，本开关缺省为关会让不带该键的旧前端整轮白跑（探完全还原）。关着时「剔除不支持」在弹层里显形失效（收敛口径无从谈起，与「探测未填充」那一档同一处理）。

## 宿主与卡片

- **RPC channel 由本插件在已注入 webServer 的子 fiber 上自注册**，不用宿主 `connection.rpc.handle`（后者在服务自己的 ctx 上求值 `owner.webServer`，而 connection 已不再注入它，必然抛错）；复用宿主 `requestRejection` 做信任围栏、按宿主 `rpcFetchHandler` 复刻信封与状态码。
- **卡片按钮取「保存」不取「应用」**：写 settings 即前端职责终点，填充由后端触发、填了几条前端无法感知。**瓦片默认收起、同时只展开一个**（官方手风琴语义）；`defaultOpen` 同时决定保存成功后是否自动收起——默认收起才自动收起（模型页 footer 席），默认展开的三席保持展开。**「取消」键仅未保存时渲染**。
- **输入框弹层用 Modal 的 headless 形态、面板照设置面板的几何**：卡片即唯一可见层，不套宿主的标题栏 / 关闭钮 / content / body 一层（那层 chrome 与卡片自身的 header 重复两层标题）。面板几何复刻设置面板 `SettingsRoot.module.css` 的 `.panel`（800px 宽、圆角与阴影同其令牌），**高度取 640px 而非设置面板的 800px**：卡片内容远不足 800px，照搬会在面板上下留出一大片容器自身区域——既无内容也就无滚动提示，点击落在容器上而非遮罩，用户既关不掉也看不出边界。640px 够放下多数瓦片的常用视域，超出即在包裹层内滚动；`.root` 是 `align-items:center` 的 flex 容器，故面板须 `flex:none`，否则固定高度被 flex 收缩吃掉、不居中。**该席禁折叠**（`collapsible={false}` 恒展开并渲染静态头）：面板尺寸固定、内容可滚，折叠只会让内容与指针下的尺寸脱钩。
- **浏览器半的整套编排挂在 `configForms` 子 fiber 上，不挂插件父 ctx**：`apply` 在 `ctx.inject(['configForms','connection'])` 的回调里把该回调的 `child` 传给 `boot`。挂父 ctx 时子 fiber 卸载不清理那些注册（cordis 的 `ctx.effect` / `ctx.slots.inject` 只归调用方自身 fiber），而 `configForms` 换实例即让子 fiber 重建、回调重跑——第二次 `locale.register(CARD_NS)` 撞宿主 `already has locale` 抛错，slot 注册也跟着重复；挂子 fiber 则重建前先级联撤销，往复安全。`locale` / `slots` 仍只写在父级 inject 里：子 ctx 取服务沿父链上溯，不必重复声明（宿主机制见 `host-api.md`「装载与 HMR 契约」节）。
- **「UI 与行为」组（`behavior`）管的是 UI 装卸，不是插件行为**：四个开关只决定各 UI 部件在不在，插件功能本体（参数填充、compat、记忆、跟随、自调档位）一律照常运行。
- **开关必须落到「注册 / 撤销注册」，组件内显隐不够**：`settings.plugins.tab` 的 tab 头是宿主按**注册账本**画出来的，组件返回 `null` 只让内容空掉、tab 头照旧——用户点进去是一个空白选项卡。故受管的四个部件一律经 `ctx.slots.inject`，在宿主声明到达后的回调里订阅配置，开则 `ctx.slots.register`、关则调该次注册的 disposer 撤销条目（撤销触发 `slots/changed` 重挂载）。幂等靠闭包内 `mounted` 记「当前是否已挂载」，目标态与已挂载态一致时不动，故配置反复通知（含无关组的变更）不重复注册。
- **注册动作必须写在 `inject` 回调里，不能在 `apply` 里按开关直接 register**：向未声明的 slot 注册会抛 `slot "..." is not declared`（`ui-slots/src/index.ts`），而声明到达前本席不能注册——**该抛错发生在 fiber 启动期，会连累同一 fiber 里后续的全部注册**（本插件实测：五席全没注册，连记忆监听与界面语言上报也一起没跑，症状是「开关全开但一个界面都没有」）。`inject` 回调返回的清理函数会被宿主挂进该次声明的 effect，故回调内部自建订阅、返回退订与撤销即可，生命周期仍归宿主管。
- **工具栏的两枚 chip 各占一个席位条目**：宿主 list 席位按 `id` 记账、`id` 唯一而 `id` 不同可并存，故「模型优化」与「跟随」各注册一条（`order` 5 / 6 决定先后），各由 `behavior` 的一个开关支配——两者管的事本不相关，一个管"在哪打开设置"，一个管"当前是否在跟随"。渲染点只有一个（`InputBar` 一次 `renderSlot` 画出该席位全部条目），两者间距即宿主 `.tools { gap: 12px }`。
- **工具行 chip 的字色分三档语义（弱化 / 生效 / 失败），弱化档内再分两级色深**：模型优化恒用 `label-secondary`；跟随灯未生效降到 `label-caption`，与宿主 `ModelSelect.module.css` 的 `.triggerEffort`（当前推理级别）同色——它表达的同样是「有个值摆在那里、此刻却不参与决策」，与模型名同权就会把关闭误读成正常状态。生效态 success 绿、失败态 warn 琥珀，另在 chip 内补 6px 状态点，非生效态不画点，故关闭与弱化除色深外还有形状差。
- **「插件管理」是唯一不可关闭的入口，故它不落配置**：它在瓦片里是一条恒开且禁用的展示行（`tile.tsx` 的 `lockedRow`），不绑任何配置键、不进 `GROUP_KEYS`——故组总控、草稿、脏检测都看不见它。给了开关就会出事：关掉之后除插件详情页与组件实例详情页外无处可去，用户再也打不开任何界面来把它改回来。
- **可见性判据的缺省方向与其它组相反**（`behaviorVisible`）：其余组缺字段落该字段的出厂默认（多为 `true`，但语义是「这项行为开启」），本组缺字段落**可见**——段还在 loading 时若落不可见，首屏会凭空少一块界面且用户不知道是加载中还是被关了。组内取值仍按严格布尔判，只有显式 `false` 才卸载。
- **瓦片总控开关按 `every` 显示**：组内全开才显示开，部分选中显示关，点击即整组补全为开。用 `any`（任一为开即开）会误导且点击会把用户已勾的那几行**抹掉**（他本意是补全）。口径与验证弹层的分组「全选」统一。代价：从部分选中到整组全关需点两次（先全开再全关）。总开关本身无存储，只是个批量操作。
- **卡片末尾固定一条版权 / 联系行**（分割线 + 地址 / 版本 + 两个跳转键），三元素同款、不做主次层级；「问题反馈」指向 `/issues/new?body=` 预填「标准 issue 模板 + 插件版本」，占位符用 `--要填什么--`。**卡片底部自上而下三段**：动作键行（强制更新 / 重置推理级别 / 恢复备份 / 验证模型，靠左起排、组内可换行、**位于分隔线之上**——键数增长后不再与取消/保存相互挤压）、分隔线 + 取消/保存（靠右 `flex-end`）、分隔线 + 联系行。动作键行刻意不设分割线：它承接上方瓦片，分隔线只用来分开「卡片正文」与「页脚操作/信息」。`.dsh-mf-actions` 是三处键组共用的容器，故换行能力加在它身上而非逐行另设。
- **不引入 `failed` 态、不做「恢复默认」**：三组布尔恒合法、写入为单字段原子写，失败时 `dirty` 已传达该信息；官方 reset 依赖字段级 user/base 分层与"未填回落"语义，本插件是整体显式快照。
- **对外报告状态的文案一律以句号收尾**：状态行是卡片上唯一承载「刚才那次操作结果」的位置，同一位置时而句号收尾时而戛然而止，读起来像两种语气。范围是全部对外报告状态的行——`setNotice` 的十二个结果键（`saveDone` / `forceDone` / `forceNone` / `forceFailed` / `resetDone` / `resetFailed` / `restoreDone` / `restoreFailed` / `pruneDone` / `pruneFailed` / `clearEffortsDone` / `clearEffortsFailed`）、`role="status"` 的加载与只读两行、字段级 `role="alert"` 的排除 id 报错，以及宿主服务缺失时卡头那行 `unavailable`——中英文案同改。**两类文案不在此列**：加载中的省略号本身即行尾标点；验证记录区的逐条结果（`provider: model [effort]：可用`）与「已跳过 N 项」是数据条目而非句子，加句号反而不成体例。
- **「隐藏官方API」拦在模型目录生成处，不改官方 provider 的配置**：宿主 UI 的模型目录只有一条生成链路（`modelCatalog` 远程 → `buildModelCatalog` 逐 provider 调 `ctx.llm.listModels`，末了滤掉模型数为 0 的组），故在 `listModels` 上以实例自有属性遮一层、命中即返回空清单即可，过滤发生在列表生成后、UI 显示前，前端零改动。**不写官方 provider 的 `models` 配置**：那条路实测不生效——官方适配器对 `models` 有 `.default(DEFAULT_MODELS)` 兜底，出厂即带一整份默认模型表，清空配置并不等于目录里没有模型；且写配置要先备份再回填，插件崩溃或用户中途改配置就会留下半截状态，代价远高于收益。判定口径与「设置→模型」的小红点同源（同一份 `apiKeyEnv` → `credentials.describe().configured`），凭据服务缺席、目录里没有该提供方、引用名语法非法、读取抛错——四种情况一律放行不隐藏：过滤是展示层诉求，判不准时宁可照常显示。
- **名单只放 `deepseek-official`，不放 `deepseek-account`**：account 段 profile 没有 `apiKeyEnv` 键（认证只走 `ctx.deepseekAccount` 的 token），`apiKeyEnvOf` 会回退到 `DEFAULT_OFFICIAL_API_KEY_ENV = 'DEEPSEEK_API_KEY'`，于是「已登录账号但没配 `DEEPSEEK_API_KEY`」的用户会被误判未配置、被本插件隐藏一个本来可用的账号模型组；而且该 provider 自 `0.1.7-rc.2` 起自带登录门（`discoverModels` 未登录即返回空清单），无需外部兜底。**功能本身保留**：宿主自 `0.2.1-alpha.2` 起对 `deepseek-official` 做了同一件事（`llm-deepseek-api-key` 的 `discoverModels` 在 `MISSING_CREDENTIAL` 时返回 `[]`），故本功能在新宿主上是冗余但无害的兜底、在老宿主（≤ `0.2.1-alpha.1`）上仍是唯一手段——删掉它会把老宿主用户暴露回「挂着一组用不了的官方模型」。
- **「隐藏官方API」不挂任何事件，判定逐次实时现算**：遮蔽的是全部消费者共用的一处（目录生成、会话可用性校验、记忆剪枝都走 `listModels`），缓存判定会让「开关已翻转 / 密钥刚配上」与「旧结论」不一致；而 UI 目录的刷新本就由宿主浏览器侧服务负责（`settings/document-updated` 与两个 `credentials/*-updated` 事件任一到达即 `catalog.refresh`），插件侧再挂一遍只会得到重复评估。代价是每次目录生成对该提供方多一次凭据 `describe`（本地读存储与 `.env`，不打网络），可接受。
- **遮蔽层的卸载只清状态位，不动服务上的属性**：卸载钩子把模块级的活状态位置回 `false`，遮蔽层留在 `llm` 上、退化成直通原方法。**不 `delete` 属性、也不写回原函数**：遮蔽是链式的，后装插件记住的 `original` 正是我们的遮蔽层，卸载时若去动属性，`delete` 会让查找落到别人的层上（等于替别人卸了载），写回则会连别人的遮蔽一起抹掉——两者都建立在「此刻没人压在我上面」这个不成立的前提上。只清状态位则与别人的遮蔽完全解耦：谁压在哪一层都无所谓，我们这层自己会退化。附带解决失活 ctx 的报错：判定要读 `ctx.llm` / `ctx.credentials`，fiber 失活后访问即抛 `cannot get required service "llm" in inactive context`，状态位先判、判到 `false` 即直通，卸载后不再碰 ctx。遮蔽层残留的只有 `llm`（宿主服务）与 `original`，都不随插件消亡。
- **「本地化推理级别」换在 Node 半的 `ctx.llm.resolveModelInfo` 这一层**：档位显示名只在它的返回里出现（`buildModelCatalog` 先 `listModels` 拿模型、再 `resolveModelInfo` 拿档位元数据，后者才有 `efforts[].name`），UI 菜单、触发器标题与 subagent 的 list-models 工具全取这个名字——遮这一处即全链覆盖，且与 `official-filter` 遮 `listModels` 同一对象、同一形态（公开实例方法，赋值遮蔽已验证）。**不走浏览器半**：目录 store 是 zustand + immer `freeze`（原地改写被冻结挡下）、目录实例藏在 `ModelDirectoryResolver` 的私有字段里、`ctx.remote.session` 与 cordis 服务键 `remote.session` 不是同一个对象（实测 `===` 为 false，按服务键遮蔽装得上却零调用，是静默失效的坑）——三条路都比 Node 半一个实例方法的面大。代价与取舍：`tool-subagent` 的 list-models 工具把 `effort.name` 拼进给 AI 的文本，开关开启时 **AI 看到的档位名也是中文**（其余消费者只取 `context` / `inputModalities`，已逐一核实零影响）。
- **`defaultEffort` 不翻译**：它是档位 id 而非名字，宿主 `LlmRuntime` 校验它必须落在 `efforts[].id` 集合内（不合法即抛 `INVALID_MODEL_REASONING`）——翻译即破坏校验与线上值。UI 显示默认档位走「id → 对应档位 name」，那个 name 已被换掉，显示链路自然覆盖。
- **语言判定三路取值、逐级回退**：Node 侧没有 `locale` 服务、读不到浏览器自动探测，故 ① 宿主 settings 文档 `locale.preference`（用户显式选择，落盘持久，Node 经 `descriptorOf`/`sectionOf` 直读）；② 浏览器半启动时经 RPC 端点 `reportLocale` 上报探测语言（进程内易失，重启由浏览器重新上报）；③ 回退 `en` 不换名。注意 volatile 是配置 schema 的必写形式、与是否落盘无关——`preference` 就是持久字段。
- **词表键取宿主口径的显示名形式，键集挂共享层档位表**：`EFFORT_NAMES_ZH` 的键不是原始 id，而是宿主适配器算显示名用的那个表达式（`id` 首字母大写）——查表键与用户在界面上看到的英文逐字对得上，词典可直接对照 UI 校对；键集由共享层的 `EFFORT_LEVELS`（跨半共享，与 harness 的 ModelThinkingLevel 一致）约束，`test/effort-name.test.ts` 断言键集逐项相等且各值非空。**id 非全小写的档位（如 `HIGH`）不换名**：宿主对它的显示名是 `HIGH` 而非 `High`，不落七键，原样透传交给其作者命名——按宿主公式查表，不做大小写无关的猜测。**`Default` 也在同一张表内**：它是宿主 `ModelSelect.tsx` 自合成的伪菜单项（不属 `EFFORT_LEVELS`），译名与七档同表维护、避免散落硬编码；代价是该表类型只能是 `Record<string, string>`，键集改由上述测试兜住而非编译期。
- **「显示原档位名」开关：中文后追加「 · 」与原档位名，两个开关都默认开**：翻译后单看「最大」无从判断对应哪个档位，故 `showOriginalEfforts`（默认 true）在中文名后追加 `` `${中文} · ${原档位名}` ``（分隔符取共享常量 `EFFORT_NAME_SEP`，原档位名直接用宿主给的 `efforts[].name` 原值、不重算）。三态：`localizeEfforts` 关 → 原样英文档位名；开而 `showOriginalEfforts` 关 → 纯中文；两者都开 → 「中文 · 原档位」。**Default 伪菜单项同步三态**（`src/client/locale-patch.ts` 的 `valueOf`，与 Node 半 `localizeEffortNames` 拼同一分隔符常量防走样）——它走浏览器半词典注入而非 `resolveModelInfo`，是换名链路唯一不共用的分支。
- **Tooltip 方向一律 `side="top"`**：设置页卡片上方有 header、弹层位于视口中央，上方始终有足够空隙；help 图标都在行内左侧或中间，气泡从上方弹出不会被右侧滚动条或卡片边缘裁掉，统一方向也避免视觉抖动。不用 `side="right"` 是因为瓦片展开体的帮助图标贴近行尾，右侧空间窄。

## 档位自调

- **让 AI 自调档位 = 注入两枚工具与一段提示词**：档位该多高取决于「当前任务有多难」，这个判断天然长在会话过程里、AI 手里信息最全，插件能看到的只有配置文件。开关打开即装、关闭即卸（注入面随自有段变更热更）；插件自身不存任何档位状态——待生效选择与投影全在宿主，HMR 与开关往复都无损。
- **设置走 UI 同款 `sessionController.selectModel`**：与用户在模型选择器里选档完全同一条链路（落 `model/selection` 事件 → 投影 `pending` → 下一次请求生效），宿主照常做适配器元数据校验。不走 `agent/request` 改写、也不直写 `llm-pi-ai` 段：前者是子智能体跟随的领地且只影响单次请求，后者绕开宿主的模型校验、还把「会话级选择」降格成「全局配置」。
- **查询走 `llm.resolveModelInfo`（全量提供方），不读 models.dev 目录**：可用档位与默认档位的权威来源是适配器元数据（宿主校验用的就是它），目录缓存只是填充时的静态参考；两边不一致时以宿主口径为准，才能保证「查出来的档位一定设得进去」。查询与设置共用同一条当前路由回落链（投影 `pending` → `lastUsed` → 请求头 → Agent options，与 `src/subagent.ts` 的取法同一条规则），`adapterDefaults.reasoningEffort === true` 视为未选档位。
- **档位值一律用 `efforts[].id` 实际值，不设 `'default'` 哨兵，出参也不出现 `defaultEffort`**：档位 id 由适配器自定（`off` 不一定存在、语义也未必是「默认」），自造哨兵就得在工具出参、提示词与宿主校验三层各解释一遍「`default` 是什么」；而 AI 发起的调整实际只有升 / 降两个操作（保持 = 不发请求），「默认档位」对它毫无用处——AI 读到的每个字段都该有用处，无用的字段只会污染注意力。
- **唯一失败形态是「模型不支持该档位」，`RemoteError` 原样透传**：宿主已经归一好了失败面（不支持档位、子智能体会话被拒等），工具再分类改写只会丢信息；`set` 的入参失败（非字符串 effort、无路由）回业务失败值（`ok:false` + `error`）而非抛错——AI 读得到原因才谈得上自行纠正。
- **「先查后设」靠提示词软指引，不做硬校验**：查询与设置之间路由可能被用户在 UI 里切换，硬校验「没查过不许设」挡不住真正的错（设了已失效的档位），只会把合法的「已知档位直接设」用法挡在门外；提示词只指明失败后的处理——重查再试一次，仍失败就保持当前档位（不再重试），其余细节不进提示词以免污染注意力。
- **四个宿主服务原经 `ctx.get` 查询式取用、不进 `inject`，现改为 `ctx.inject` 子 fiber 门控**：`tools` / `systemPrompt` / `sessionController` / `sessionProjections` 在部分宿主组合可能缺席；原方案是缺席 warn 一次、功能整体不启用、下次设置变更再重试，顾虑是插件级 `inject` 会让插件在缺服务的宿主上永久 PENDING，拖死其余全部功能——但 cordis 的 `ctx.inject(deps, callback)` 子 fiber 形态（前端 `src/client/index.tsx` 消费 `configForms` 同款）没有这个问题：四者全部就绪才执行回调，任一缺席仅该子 fiber PENDING（静默，不拖累主功能），服务后来注册时自动执行，原「下次设置变更重试」由框架的注入语义接管。工具与提示词的 disposer 挂在宿主服务自己的 ctx 上，子 fiber 卸载不会自动清理，须经 `ctx.effect` 手动调；注册中途抛错（如同名工具冲突）时回滚已注册部分，保持无痕。
- **`selfTune` 与 `followParent` 同批落在 `userExperience` 组内、不递增 `CONFIG_VERSION`**：同为会话侧体验开关、与模型配置写入无关、同样不读 `excludes`；解析端对缺键落默认（false），台阶产物补同一默认即保住「DEFAULT_STORED 与升级链空输入一致」的不变量（台阶写法见 `src/upgrade.ts` 的 `V8_SELF_TUNE_DEFAULT`）。
